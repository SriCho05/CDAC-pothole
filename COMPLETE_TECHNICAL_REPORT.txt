GLOSSARY OF KEY TECHNICAL TERMS
=====================================================================

BATCH / BATCH SIZE
------------------
A "batch" is a group of input images processed together in a single 
forward pass through the neural network.

- Batch = 1: Process 1 frame at a time (sequential)
- Batch = 4: Process 4 frames simultaneously (parallel)

Why it matters: GPUs have thousands of cores. Processing 4 frames at once
keeps more cores busy, improving hardware utilization. However, larger
batches need more GPU memory and increase latency per frame.

In our model: Input tensor shape is [Batch, 3, 640, 640] where 3=RGB channels.

THROUGHPUT vs LATENCY
---------------------
- LATENCY: Time to process ONE batch (milliseconds). Lower = better responsiveness.
- THROUGHPUT: How many batches/frames per second (FPS). Higher = more capacity.

Key distinction: Batch=4 has HIGHER latency (38ms) but HIGHER throughput (105 FPS)
because 4 frames complete in 38ms = 105 frames/sec.

QPS (Queries Per Second) vs FPS (Frames Per Second)
----------------------------------------------------
In trtexec output: "Throughput: 26.4 qps" at batch=4 means 26.4 BATCHES/second.
Since each batch has 4 frames: 26.4 × 4 = 105.6 FRAMES/second (FPS).

trtexec reports QPS (batch rate). We convert to FPS for clarity.

trtexec (TensorRT Execution Tool)
---------------------------------
NVIDIA's official command-line benchmarking tool for TensorRT engines.
- Runs inference directly in C++ (no Python overhead)
- Measures true GPU compute performance
- Used for: engine validation, performance profiling, accuracy testing
- Command example: trtexec --loadEngine=model.engine --shapes=input:1x3x640x640

This is the GOLD STANDARD for TensorRT performance. Python results will
always be lower due to interpreter overhead.

H2D / D2H (Host-to-Device / Device-to-Host)
--------------------------------------------
- H2D: Copy input data from CPU RAM (Host) to GPU VRAM (Device)
- D2H: Copy output results from GPU VRAM back to CPU RAM

These transfers happen over PCIe / unified memory bus and take time.
On Jetson Orin (unified memory): H2D ~0.9ms, D2H ~0.1ms per frame.
In trtexec: "--noDataTransfers" skips these to measure pure compute.

FP16 / INT8 / FP32 (Precision Modes)
------------------------------------
- FP32 (Float32): 32-bit floating point. Standard PyTorch precision. Slowest.
- FP16 (Float16/Half): 16-bit floating point. 2x Tensor Core throughput. 
  Default for TensorRT on Jetson. Minimal accuracy loss (<0.5% mAP).
- INT8 (Int8): 8-bit integer. 4x Tensor Core throughput vs FP32.
  Requires calibration dataset. Best speed but harder to deploy.

Tensor Cores: Specialized GPU cores for matrix multiply-accumulate.
FP16 Tensor Core ops = 2x FP32 CUDA core ops. INT8 = 4x.

OPTIMIZATION PROFILES (Dynamic Batching)
----------------------------------------
TensorRT feature allowing ONE engine to support MULTIPLE input shapes.
Instead of building separate engines for batch=1, batch=2, batch=4,
you build ONE engine with profiles:

  --minShapes=images:1x3x640x640   (minimum batch=1)
  --optShapes=images:2x3x640x640   (optimized for batch=2)  
  --maxShapes=images:4x3x640x640   (maximum batch=4)

At runtime: context.set_input_shape('images', (batch, 3, 640, 640))
TensorRT picks the best pre-tuned kernels for that batch size.

CUDA STREAMS
------------
Asynchronous execution queues on GPU. Multiple streams allow overlapping:
- Stream 1: H2D copy for frame N+1
- Stream 2: GPU compute for frame N  
- Stream 3: D2H copy for frame N-1

This hides transfer latency behind compute. Essential for high FPS.

PINNED / PAGE-LOCKED MEMORY
---------------------------
cuda.pagelocked_empty() allocates CPU memory that CANNOT be swapped to disk.
- Enables DMA (Direct Memory Access) for faster H2D/D2H transfers
- Required for async cudaMemcpyAsync()
- Without it: transfers fall back to slow staging buffers

TENSORRT ENGINE (.engine file)
------------------------------
Compiled, optimized model ready for deployment. Contains:
- Layer fusion (Conv+BatchNorm+ReLU → single kernel)
- Precision calibration (FP16/INT8)
- Kernel auto-tuning (fastest algorithm per layer)
- Memory layout optimization
- Serialized for fast loading (~100ms vs minutes for ONNX parse)

NATIVE vs PRACTICAL FPS
-----------------------
| Term | Meaning | Our Results |
|------|---------|-------------|
| Native FPS | trtexec C++ runtime, no Python | 105 FPS (batch=4) |
| Practical FPS | Python + OpenCV + postprocessing | 39 FPS (batch=4) |
| Display FPS | With cv2.imshow() GUI | 24 FPS |

The gap (105 → 39) = Python interpreter overhead (~60% of pipeline).

KEY OPTIMIZATION TECHNIQUES
---------------------------

1. Dynamic Batching (Optimization Profiles)
   - Single engine handles batch 1, 2, 4
   - Runtime shape switching via set_input_shape()
   - TensorRT selects optimal kernels per batch size
   - 2x throughput gain at batch=4 vs batch=1

2. FP16 Precision
   - 2x compute throughput vs FP32 on Tensor cores
   - Minimal accuracy loss (<0.5% mAP)
   - Default for Jetson Orin Tensor cores

3. Pinned Memory & Async Transfers
   - cuda.pagelocked_empty() for host buffers
   - cudaMemcpyAsync + CUDA streams
   - Overlapped H2D/compute/D2H

4. Batch Inference Amortization
   - Python loop overhead ~10ms/frame
   - Batch=4 spreads overhead across 4 frames
   - Net: 39 FPS vs 36 FPS (8% improvement)

5. Memory Optimization
   - Workspace: 64MB default sufficient
   - Dynamic engine smaller than static (25MB vs 30MB)
   - INT8 calibration limited to 500 frames to avoid OOM
