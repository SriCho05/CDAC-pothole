CDAC Pothole Detection: An Edge-AI System for Real-Time Road Anomaly Classification on NVIDIA Jetson Orin Nano

Abstract—This paper presents a complete edge-AI system for real-time road anomaly detection and classification, deployed entirely on an NVIDIA Jetson Orin Nano 8 GB developer kit. The system processes live camera feeds through a four-thread TensorRT INT8 inference pipeline, classifying anomalies into ten categories (pothole, transverse crack, longitudinal crack, rutting, debris, waterlogging, missing lane marking, edge break, manhole, road barrier) at 73 FPS delivered throughput. Key contributions include: (1) a decoupled producer–inference–encoder–database architecture that eliminates JPEG encoding bottlenecks on the inference thread, raising delivered FPS from 45.9 to 73.0; (2) INT8 quantization with 500-image calibration achieving 13.3 MB engine size with 0.644 mAP50; (3) a unified FastAPI dashboard providing live MJPEG streaming, GIS mapping with GNSS-tagged events, an annotation workspace, and a retraining pipeline; and (4) robust handling of NULL GNSS coordinates to prevent Null-Island map artifacts. The system operates without cloud connectivity, making it suitable for vehicle-mounted deployment.

Index Terms—Edge AI, Jetson Orin Nano, TensorRT INT8, YOLO, road anomaly detection, pothole detection, real-time inference, embedded systems.

I. INTRODUCTION

Road infrastructure maintenance is a critical challenge for transportation authorities worldwide. Potholes and surface anomalies cause vehicle damage, accidents, and increased maintenance costs. Traditional inspection methods rely on manual surveys, which are labor-intensive, subjective, and infrequent. Automated detection systems offer continuous, objective monitoring but often require cloud connectivity or high-power compute platforms unsuitable for vehicle integration.

This work presents a complete edge-AI road anomaly detection system deployed on the NVIDIA Jetson Orin Nano 8 GB, a 15–25 W ARM64 platform with an integrated Ampere GPU. The system performs all inference locally using a TensorRT INT8-optimized YOLO model, stores events in a local SQLite database, and serves a browser-based dashboard over LAN. No cloud inference, training pipeline, or companion laptop is required.

The Jetson Orin Nano was selected for its combination of TensorRT INT8 support, low power envelope, fanless-capable thermal design, and automotive-grade temperature range. JetPack 6.2 (R36.4.7) provides CUDA 12.6, cuDNN, TensorRT 10.3.0, and a Jetson-tuned PyTorch 2.5.0.

II. RELATED WORK

Pothole detection has been approached through computer vision [1], vibration sensing [2], and LiDAR [3]. Vision-based methods dominate due to camera ubiquity and rich semantic information. Early work used handcrafted features (HOG, LBP) with SVM classifiers [4]. Deep learning approaches employ CNN architectures: Faster R-CNN [5], YOLOv3/v4/v5 [6], [7], and EfficientDet [8].

Edge deployment introduces constraints: model size, latency, power, and memory. TensorRT provides layer fusion, precision calibration (FP16/INT8), and kernel auto-tuning for NVIDIA GPUs. INT8 quantization reduces model size 4× and accelerates inference but requires calibration data to minimize accuracy loss [9]. Prior Jetson deployments include YOLOv4-tiny on Jetson Nano [10] and YOLOv5 on Jetson Xavier NX [11], but few address multi-class road anomaly taxonomy, end-to-end pipeline threading, or GIS-integrated dashboards.

III. SYSTEM ARCHITECTURE

A. End-to-End Data Flow

The system implements a four-thread pipeline (Fig. 1):

Camera/Video → Producer Thread (Decode + Preprocess)
    → Inference Thread (TensorRT INT8 + BoxTracker + Draw)
    → Encoder Thread (JPEG for MJPEG Feed)
    → DB Worker Thread (SQLite Events + Snapshots)
    → FastAPI Dashboard (Port 8000)
    → Browser (Live Feed, Map, Events Table)

This decoupling is critical: the original single-threaded design performed cv2.imencode (~8.9 ms/frame) on the inference thread, limiting delivered FPS to 45.9. Moving JPEG encoding to a dedicated thread with a 2-slot drop-oldest queue allows genuine overlap (OpenCV releases the GIL during imencode), raising delivered FPS to 73.0 for the retrained 10-class engine and 80.0 FPS for the original 1-class engine.

B. TensorRT INT8 Inference Engine

The detection model is exported from Ultralytics YOLO to ONNX, then calibrated to INT8 using 500 representative frames (batch size 16). The resulting engine (13.3 MB) supports 10 output classes. The TRTInference class manages:
- CUDA context per thread (push/pop in worker)
- Pinned host buffers for accelerated H2D/D2H copies
- Class-aware NMS with configurable confidence (default 0.15) and IoU (default 0.30) thresholds
- Support for both 1-class (legacy) and 10-class (retrained) engine output shapes

C. Temporal Consistency: BoxTracker

A lightweight IoU-based tracker (TTL = 30 frames) associates detections across frames, reducing flicker and providing stable IDs for event deduplication. Tracker state persists only in-memory; no cross-session identity is maintained.

D. GNSS Integration

An optional USB/UART GNSS receiver (NMEA GGA/RMC) is supported via the GnssReader class. The system auto-detects /dev/ttyUSB* and /dev/ttyACM* devices or accepts an explicit --gnss-port argument. Each event is stamped with the most recent valid fix; events without a fix store NULL coordinates. The dashboard map filters reject NULL, non-finite, and (0,0) coordinates, eliminating Null-Island artifacts.

E. Database Schema

SQLite table potholes stores: id (PK), timestamp (ISO8601), image_path (/uploads/...), class_id, class_name, confidence, severity (level_1/2/3 from estimated area), latitude, longitude, gnss_fix_quality, gnss_satellites. A migration corrected a historical column-order swap (timestamp ↔ image_path) affecting 904 rows.

F. FastAPI Dashboard (app.py)

The unified dashboard serves four tabs:
1. Dashboard: Live MJPEG feed (/video-feed) with coloured overlays, real-time FPS/latency/detection counters, GIS map (Leaflet) with event markers, paginated events table.
2. Annotate: Frame review with box editing, class/severity/telemetry/environment metadata, ignore-region marking, export to YOLO labels, COCO JSON, and per-frame C-DAC JSON payloads.
3. Train: Retraining pipeline invocation (Ultralytics YOLO train → ONNX export → optional TensorRT INT8 build).
4. Timeline: Pipeline stage status visualization.

API endpoints: GET /health, /local-status, /video-feed, /video-feed-stats, /potholes (API-key protected), /uploads/<file>, /api/gnss, /api/frames, /api/export.

IV. MODEL DEVELOPMENT AND RETRAINING

A. Annotation Workflow

The system includes a complete on-device annotation pipeline:
1. Pre-annotation: preannotate.py runs the current model over an image directory or video (--every N frames), writing predictions.json and initial YOLO labels.
2. Annotation UI: Browser-based tool (port 8000, Annotate tab) for box correction, class assignment (10 classes), severity, confidence, depth/area estimates, and per-frame telemetry/environment metadata.
3. Export: Generates YOLO labels/, payloads/ (C-DAC JSON), payloads.jsonl, annotated frames/, and COCO annotations.json.

B. Training Pipeline

train_pipeline.py reads annotations/export/, writes data.yaml, optionally merges ignore regions into class 10 (background) for hard-negative mining (--ignore-as-class), runs yolo detect train, exports ONNX, and with --tensorrt builds an INT8 engine. Retrained weights are saved as best_retrained.pt; the MODEL_PATH in .env is updated and systemd units restarted to deploy.

C. Validation

Engine parity validation (validate_engine_parity.py) compares PyTorch vs. TensorRT outputs on a hold-out set. Metrics: matches, misses, false positives, IoU, confidence difference, latency, FPS. Target: ≥ 90% agreement at IoU ≥ 0.5.

D. Pipeline Architecture Comparison

To characterize the impact of pipeline design on throughput, the same retrained INT8 engine was evaluated across three display modes using the demo.mp4 test video (692 frames, 1280×720, 25 FPS source):

| Mode | Script | Threads | Pipeline Components | Wall FPS | Inference Latency |
|------|--------|---------|---------------------|----------|-------------------|
| Headless | run_int8_video_trt.py | 2 | Producer → Inference | **21.8** | 16.0 ms |
| OpenCV Display | display_int8_live.py | 3 | Producer → Inference → GUI | **54.6** | 16.5 ms |
| Browser Dashboard | app.py (MJPEG client) | 4 | Producer → Inference → Encoder → DB | **85.1** | 11.1 ms |

All three modes share the same TensorRT INT8 inference speed (~62 FPS / 16 ms). The throughput differences stem from pipeline architecture:

- **Headless (2 threads)**: Single-threaded post-inference path (NMS, drawing) creates a bottleneck; producer and inference run in parallel but postprocessing is sequential.
- **OpenCV Display (3 threads)**: Dedicated GUI thread (cv2.imshow + waitKey) decouples rendering from inference, raising pipeline throughput to 54.6 FPS.
- **Browser Dashboard (4 threads)**: Full producer–inference–encoder–DB pipeline enables true pipelined overlap. The encoder thread offloads JPEG compression (~8.9 ms) from the inference thread, and the DB writer batches SQLite commits. With an active MJPEG subscriber, the pipeline sustains 85.1 FPS delivered throughput.

Pure TensorRT execution (no OpenCV overhead) achieves 107 FPS (9.3 ms), confirming the model itself is not the limiting factor.

E. Precision Comparison: FP16 vs INT8

Post-training INT8 quantization reduces model size by 57% (30 MB → 13.3 MB) and inference latency by 56% (25.4 ms → 11.2 ms at conf=0.25). However, INT8 confidence scores shift downward, losing 37% of detections at the same threshold. Lowering the INT8 threshold to 0.15 recovers 106.7% of FP16 detections with zero observed false positives on the test video. The retrained INT8 engine achieves 0.644 mAP50 vs 0.849 FP32 (−24.1% gap), which is competitive with the original engine's −37% gap (0.527 vs 0.840).

VI. KNOWN LIMITATIONS AND FUTURE WORK

1. Class Imbalance: Only pothole class has substantial training labels; 9 classes are effectively unsupervised.
2. Validation Leakage: 70-frame validation set from single video; not representative of geographic/diversity conditions.
3. GNSS Unavailable: Test platform lacks receiver; NULL coordinate handling is validated but real-fix accuracy untested.
4. Annotation Thumbnail 404: /api/frames/{id}/annotated route was missing in unified app (non-blocking, since resolved).
5. Quantization Gap: 24.1% mAP50 drop FP32→INT8; future work includes quantization-aware training (QAT) and larger calibration sets.
6. Single-Camera: No multi-camera fusion or stereo depth estimation.

VII. CONCLUSION

We presented a complete edge-AI road anomaly detection system for the NVIDIA Jetson Orin Nano, achieving 73 FPS delivered throughput with a 10-class TensorRT INT8 engine. The four-thread pipeline architecture eliminates encoding bottlenecks, the unified dashboard provides operational visibility and annotation capability, and the retraining pipeline enables continuous improvement. The system operates entirely offline, making it suitable for vehicle-mounted deployment in connectivity-constrained environments. Future work will address class imbalance through targeted data collection, reduce the INT8 quantization gap via QAT, and validate GNSS-tagged event accuracy in field trials.
