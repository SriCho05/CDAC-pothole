SECTION 3: FPS OPTIMIZATION PROPOSALS (WITH SENSORS)
--------------------------------------------------------------------------------

KEY INSIGHT: The bottleneck at 640×640 is pure NN inference (~45ms on Jetson).
Adding sensors doesn't directly speed up the NN — but it enables smarter
pipeline strategies that reduce HOW OFTEN and HOW MUCH of the image we process.

3.1 PROPOSAL A: ADAPTIVE RESOLUTION GATE
    Problem: 640px is overkill for most frames (empty road).
    Solution:
      - Run a 160×160 "scene change" detector every frame (cheap, ~5ms)
      - If scene is "boring" (low activity), skip full inference
      - If ROI detected, run full 640px YOLO only on that crop (~15-20ms)
    Expected: 2-3x FPS improvement, ~95% frames get cheap processing

3.2 PROPOSAL B: SENSOR-TRIGGERED INFERENCE
    Problem: Running detection every frame wastes compute on clean road.
    Solution:
      - IMU: monitor vibration/acceleration envelope
        - Low vibration = smooth asphalt = skip inference
        - Spike = rough road or impact = trigger detection
      - Lux: at night, switch to thermal-only detection (cheaper, fewer classes)
      - GPS speed: if speed < 5 km/h (stopped), run detection faster
    Expected: 5-10x FPS effective rate, power savings on battery

3.3 PROPOSAL C: ROI-BASED DETECTION (HARD NEGATIVE MINING)
    Problem: Full-frame inference processes sky, gutter, car roofs.
    Solution:
      - Use the existing "ignore" regions + a cheap foreground/motion mask
      - Extract ROI (224×224) around anomaly candidates only
      - Run YOLO on crop instead of full 640×640
    Expected: 3-4x faster per-inference (224 vs 640 = ~8x less pixels)

3.4 PROPOSAL D: ASYNC PIPELINE WITH QUEUES
    Problem: Capture → preprocess → inference → postprocess is synchronous.
    Solution:
      - Thread 1: capture (GStreamer appsink drop=true, already in codebase)
      - Thread 2: batch preprocess + GPU inference (batch=2-4)
      - Thread 3: postprocess + storage
      - Queue between threads decouples slowest stage
    Expected: Hides latency variance, smoother throughput
    Note: The existing repo commit "Dynamic batching achieves 105 FPS native"
    suggests batching is viable.

3.5 PROPOSED SOLUTION: "ADAPTIVE SENSOR-AWARE PIPELINE"
    Combine A+B+C+D into one strategy:

    FRAME N:
      1. Capture RGB + thermal + IMU (async, timestamp-synced)
      2. IMU scene-activity check (microsecond): skip or proceed
      3. If proceed: run 160×160 motion/heat-change detector
      4. If ROI found: crop from RGB, run full YOLO on 224×224 crop
      5. If YOLO fires: track with SORT/deepSORT into FRAME N+1..N+3
      6. Skip full inference for tracked frames (just update bbox via tracking)
      7. Async: store events, send to C-DAC payload queue

    EXPECTED PERFORMANCE:
      - Empty road: 8-12ms per frame (tracker update only) = ~100-125 FPS
      - Active anomaly: 20-30ms (ROI detection) = ~30-50 FPS
      - Worst case (full frame): 45ms = ~22 FPS (same as current, but rarer)

    IMPLEMENTATION TASKS (priority order):
      1. [Sensor-blocked] Write inference/capture_multispec.py
         Multi-camera + IMU + GNSS capture with PTP timestamp sync
      2. [Doable now] Add ROI inference mode to local_runner.py
         --roi-mode flag: crop inference on detection candidates
      3. [Doable now] Add SORT tracker to local_runner.py
         Track detected anomalies across frames, skip redetection
      4. [Doable now] Write inference/throttle.py
         IMU-vibration-based inference gate (configurable threshold)
      5. [Jetson-only] Build 320px INT8 engine
         python -m annotate.train_pipeline --int8 --calib-set <frames>
      6. [Jetson-only] System hardening script
