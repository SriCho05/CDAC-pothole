=============================================================

Date: 2026-09-24
Platform: NVIDIA Jetson Orin Nano (8GB)
Model: YOLOv8-based pothole detector (11M params, 28.4 GFLOPs)
Input Resolution: 640x640

---------------------------------------------------------------------
GLOSSARY OF TECHNICAL TERMS
---------------------------------------------------------------------

BATCH / BATCH SIZE
------------------
A "batch" is a group of input images processed together in a single 
forward pass through the neural network.

- Batch = 1: Process 1 frame at a time (sequential)
- Batch = 4: Process 4 frames simultaneously (parallel)

Why it matters: GPUs have thousands of cores. Processing 4 frames at once
keeps more cores busy, improving hardware utilization. However, larger
batches need more GPU memory and increase latency per frame.

In our model: Input tensor shape is [Batch, 3, 640, 640] where 3=RGB channels.

THROUGHPUT vs LATENCY
---------------------
- LATENCY: Time to process ONE batch (milliseconds). Lower = better responsiveness.
- THROUGHPUT: How many batches/frames per second (FPS). Higher = more capacity.

Key distinction: Batch=4 has HIGHER latency (38ms) but HIGHER throughput (105 FPS)
because 4 frames complete in 38ms = 105 frames/sec.

QPS (Queries Per Second) vs FPS (Frames Per Second)
----------------------------------------------------
In trtexec output: "Throughput: 26.4 qps" at batch=4 means 26.4 BATCHES/second.
Since each batch has 4 frames: 26.4 × 4 = 105.6 FRAMES/second (FPS).

trtexec reports QPS (batch rate). We convert to FPS for clarity.

trtexec (TensorRT Execution Tool)
---------------------------------
NVIDIA's official command-line benchmarking tool for TensorRT engines.
- Runs inference directly in C++ (no Python overhead)
- Measures true GPU compute performance
- Used for: engine validation, performance profiling, accuracy testing
- Command example: trtexec --loadEngine=model.engine --shapes=input:1x3x640x640

This is the GOLD STANDARD for TensorRT performance. Python results will
always be lower due to interpreter overhead.

H2D / D2H (Host-to-Device / Device-to-Host)
--------------------------------------------
- H2D: Copy input data from CPU RAM (Host) to GPU VRAM (Device)
- D2H: Copy output results from GPU VRAM back to CPU RAM

These transfers happen over PCIe / unified memory bus and take time.
On Jetson Orin (unified memory): H2D ~0.9ms, D2H ~0.1ms per frame.
In trtexec: "--noDataTransfers" skips these to measure pure compute.

FP16 / INT8 / FP32 (Precision Modes)
------------------------------------
- FP32 (Float32): 32-bit floating point. Standard PyTorch precision. Slowest.
- FP16 (Float16/Half): 16-bit floating point. 2x Tensor Core throughput. 
  Default for TensorRT on Jetson. Minimal accuracy loss (<0.5% mAP).
- INT8 (Int8): 8-bit integer. 4x Tensor Core throughput vs FP32.
  Requires calibration dataset. Best speed but harder to deploy.

Tensor Cores: Specialized GPU cores for matrix multiply-accumulate.
FP16 Tensor Core ops = 2x FP32 CUDA core ops. INT8 = 4x.

OPTIMIZATION PROFILES (Dynamic Batching)
----------------------------------------
TensorRT feature allowing ONE engine to support MULTIPLE input shapes.
Instead of building separate engines for batch=1, batch=2, batch=4,
you build ONE engine with profiles:

  --minShapes=images:1x3x640x640   (minimum batch=1)
  --optShapes=images:2x3x640x640   (optimized for batch=2)  
  --maxShapes=images:4x3x640x640   (maximum batch=4)

At runtime: context.set_input_shape('images', (batch, 3, 640, 640))
TensorRT picks the best pre-tuned kernels for that batch size.

CUDA STREAMS
------------
Asynchronous execution queues on GPU. Multiple streams allow overlapping:
- Stream 1: H2D copy for frame N+1
- Stream 2: GPU compute for frame N  
- Stream 3: D2H copy for frame N-1

This hides transfer latency behind compute. Essential for high FPS.

PINNED / PAGE-LOCKED MEMORY
---------------------------
cuda.pagelocked_empty() allocates CPU memory that CANNOT be swapped to disk.
- Enables DMA (Direct Memory Access) for faster H2D/D2H transfers
- Required for async cudaMemcpyAsync()
- Without it: transfers fall back to slow staging buffers

TENSORRT ENGINE (.engine file)
------------------------------
Compiled, optimized model ready for deployment. Contains:
- Layer fusion (Conv+BatchNorm+ReLU → single kernel)
- Precision calibration (FP16/INT8)
- Kernel auto-tuning (fastest algorithm per layer)
- Memory layout optimization
- Serialized for fast loading (~100ms vs minutes for ONNX parse)

NATIVE vs PRACTICAL FPS
-----------------------
| Term | Meaning | Our Results |
|------|---------|-------------|
| Native FPS | trtexec C++ runtime, no Python | 105 FPS (batch=4) |
| Practical FPS | Python + OpenCV + postprocessing | 39 FPS (batch=4) |
| Display FPS | With cv2.imshow() GUI | 24 FPS |

The gap (105 → 39) = Python interpreter overhead (~60% of pipeline).

---------------------------------------------------------------------
OPTIMIZATION STRATEGY
---------------------------------------------------------------------

1. DYNAMIC BATCHING WITH OPTIMIZATION PROFILES
   --------------------------------------------
   Problem: Static batch=1 engine cannot utilize batch parallelism.
   Solution: Build engine with optimization profiles for batch sizes 1-4.

   Build command:
     trtexec --onnx=best.onnx \
       --saveEngine=best_dynamic_fp16.engine \
       --minShapes=images:1x3x640x640 \
       --optShapes=images:2x3x640x640 \
       --maxShapes=images:4x3x640x640 \
       --fp16

   Result: Single engine supports batch 1, 2, and 4 at runtime via
   context.set_input_shape(). TensorRT selects optimal kernels per batch.

2. BATCH SIZE SCALING ANALYSIS
   ----------------------------
   Native trtexec throughput (frames/sec = QPS × batch):
   
   | Batch | QPS (batches/sec) | Frames/sec (FPS) | Latency (ms) |
   |-------|-------------------|------------------|--------------|
   | 1     | 83.4              | 83.4             | 12.0         |
   | 2     | 48.2              | 96.4             | 20.7         |
   | 4     | 26.4              | 105.6            | 37.9         |

   Key insight: Batch 4 delivers 105.6 FPS (1.75x batch=1).
   Diminishing returns above batch 4 due to memory bandwidth saturation.

   Trade-off: Higher batch = higher throughput BUT higher latency.
   - Batch=1: 12ms latency (good for real-time control)
   - Batch=4: 38ms latency (good for max throughput)

3. PYTHON BINDING OVERHEAD - WHY 39 FPS NOT 105 FPS
   -------------------------------------------------
   Measured Python pipeline components (per frame, batch=4):
   
   | Component                    | Time (ms) | % of Total | Explanation |
   |------------------------------|-----------|------------|-------------|
   | Preprocess (resize, norm)    | 6.0       | 15%        | OpenCV + NumPy on CPU |
   | H2D Transfer                 | 0.9       | 2%         | CPU→GPU copy (async) |
   | GPU Compute (TensorRT)       | 23.4      | 58%        | Actual inference |
   | D2H Transfer                 | 0.1       | <1%        | GPU→CPU copy |
   | Python Loop/Postprocess      | 10.0      | 25%        | Interpreter + NMS + draw |
   | **Total per frame**          | **40.4**  | **100%**   | **= 24.7 FPS theoretical** |

   Why batch=4 gets 39 FPS not 24 FPS: The 10ms Python overhead is AMORTIZED
   across 4 frames. Per-frame Python cost drops from 10ms → 2.5ms.
   
   Remaining gap to native: Python GIL, memory copies, lack of CUDA Graphs.

4. MEMORY MANAGEMENT
   ------------------
   Challenges: Jetson Orin Nano 8GB shared memory (CPU + GPU).
   
   - Static FP16 engine: ~30 MB
   - Dynamic FP16 engine (3 profiles): ~25 MB (smaller due to tactic pruning)
   - INT8 calibration cache: ~2 GB during build
   
   OOM (Out of Memory) failures during INT8 build resolved by:
   - Reducing calibration set from 2000 to 500 images
   - Using --fp16 fallback for layers unsupported in INT8
   - Limiting workspace memory (default 64MB sufficient)

5. PRECISION OPTIMIZATION
   -----------------------
   FP16 selected over INT8 due to:
   - INT8 build failures (concatenation layer axis mismatch in YOLO neck)
   - FP16 provides 2x speedup over FP32 with minimal accuracy loss
   - Dynamic batch profiles only stable with FP16 on this model
   
   Accuracy validation: FP16 vs FP32 mAP difference < 0.5% on validation set.

---------------------------------------------------------------------
DEPLOYMENT RECOMMENDATIONS
---------------------------------------------------------------------

1. FOR MAXIMUM THROUGHPUT (C++ Deployment)
   ----------------------------------------
   - Use dynamic FP16 engine at batch=4
   - Expected: 105 FPS sustained
   - Implement CUDA Graph capture (cuGraph) to eliminate kernel launch overhead
   - Use TensorRT IExecutionContext::enqueueV3() with CUDA streams
   - Consider multi-GPU if available (Orin NX / AGX)

2. FOR PYTHON DEPLOYMENT
   ----------------------
   - Use dynamic FP16 engine at batch=4
   - Expected: 39 FPS sustained
   - Multiprocessing option: 2 processes × batch=2 = ~70 FPS combined
   - Or rewrite hot path (preprocess + postprocess) in Cython/C++

3. FOR LATENCY-CRITICAL APPLICATIONS
   ----------------------------------
   - Use batch=1: 83 FPS native, 36 FPS Python
   - Lower latency (12ms vs 38ms at batch=4)
   - Better for real-time control loops, autonomous braking

4. FUTURE OPTIMIZATIONS
   ---------------------
   - INT8 quantization (2-3x speedup potential) - resolve concat layer issue
   - Model pruning / distillation to smaller backbone (YOLOv8n → 3M params)
   - TensorRT 10+ weight streaming for larger models
   - Multi-stream inference (parallel contexts on separate CUDA streams)
   - CUDA Graphs in Python (experimental support in PyCUDA)

CONCLUSION
---------------------------------------------------------------------
Dynamic batching with TensorRT optimization profiles delivered 105 FPS native
throughput, exceeding the 60 FPS requirement by 75%. The primary
limitation is Python interpreter overhead (~60% of pipeline time).
For production deployment requiring >60 FPS, a C++ TensorRT runtime
is recommended. The dynamic FP16 engine is production-ready and
supports variable batch sizes for flexible throughput/latency tradeoffs.

KEY TAKEAWAY: "105 FPS" is the hardware's true capability (measured by trtexec).
"39 FPS" is what you get in Python today. Both are correct - they measure
different layers of the stack. Choose deployment language based on your
actual FPS requirement.
